# 03-16. 비-LLM 긴급 푸시 및 세션 재해복구(DR) 운영 정책

> **문서 상태**: 확정 및 운영 적용 (Active)  
> **최초 작성일**: 2026-09-23  
> **소관 부서**: purePDFrend 에이전트 거버넌스 및 품질관리실  
> **상위 규정**: AGENTS.md v2.1 (하네스 생명주기 및 세션 거버넌스 규제)

---

## 1. 목적 (Purpose)
본 정책은 LLM 토큰 소진, 플랫폼 과부하(`overloaded`), 또는 대화 세션 행(Hang/Freeze) 발생 시, 에이전트(LLM)의 응답 불능 상태와 무관하게 **최종 승급 이후 변경된 모든 작업 소스(코드, 문서 등)를 안전하게 원격 작업 브랜치에 Push**하고, 다른 세션에서 지체 없이 작업을 승계할 수 있는 **비-LLM(Non-LLM) 세션 재해복구(DR, Disaster Recovery) 절차**를 규정함을 목적으로 합니다.

---

## 2. 비-LLM(Non-LLM) 긴급 푸시 운영 원칙

### [규칙 2.1] LLM 독립적(Non-LLM) 바이패스 푸시 원칙
- 토큰 소진 및 세션 행이 발생하면 에이전트 채팅 인터페이스는 명령을 수신하거나 도구를 실행할 수 없습니다.
- 따라서 purePDFrend 웹 서비스의 Node.js 백엔드(`server.ts`)와 프론트엔드 UI 간의 독립된 HTTP 통신 채널(`POST /api/agent/emergency/push`)을 통해 **LLM 호출을 전혀 거치지 않고 GitHub Git Database API를 직접 구동하여 원격 브랜치에 즉시 Push**합니다.

### [규칙 2.2] 자동 비상 푸시의 통제 및 수동 트리거 원칙
- **오동작 방지 원칙**: 에이전트나 모델별 토큰 소비 실측 집계가 100% 완전 통제 상태에 도달하기 전까지, **무분별한 백그라운드 자동 푸시(Auto-Checkpoint Push)는 엄격히 금지**합니다.
- 긴급 푸시는 오직 다음 두 가지 경로를 통해서만 발생합니다:
  1. **사용자 수동 트리거**: purePDFrend 웹 화면 상단의 `[🚨 긴급 소스 GitHub Push]` 버튼 클릭
  2. **명시적 승인 하의 스냅샷 백업**: 세션 전환 직전 사용자의 확인을 거친 세션 백업 트리거

---

## 3. 세션 재해복구(DR) 및 `#세션복구` 운영 절차

### [규칙 3.1] 세션 긴급 스냅샷 생성
- 세션 포화(150,000 토큰 초과) 또는 이상 징후 발생 시, 웹 UI의 `[세션 긴급 백업]`을 실행하여 현재 진행 중인 세션 번호, 최근 완료 태스크, 진행 중인 루프, 미반영 파일 목록을 PostgreSQL DB(`aiagent.harness_session_meta.doc_payload.recovery_snapshot`)에 보존합니다.

### [규칙 3.2] `#세션복구` 인입 시 분기 처리 규약
새로운 세션 또는 다른 계정의 에이전트 환경에서 복구 명령어 인입 시 다음 규칙을 엄격히 준수합니다:
1. **단일 백업 타겟팅 (1건 존재 시)**:
   - 복구 대기 상태의 백업 스냅샷이 정확히 1건인 경우, 사용자에게 추가 선택을 요구하지 않고 **해당 세션을 자동 타겟팅하여 즉시 컨텍스트를 복원하고 중단된 작업의 후속 프롬프트를 제시**합니다.
2. **다건 목록 선택 (2건 이상 존재 시)**:
   - 복구 대기 스냅샷이 2건 이상인 경우, `[스냅샷 번호, 세션ID, 작업태스크명, 백업일시, 잔여 쿼터]` 목록을 표 형태로 제시하고 사용자가 복구 대상 번호를 선택하도록 유도합니다.
3. **직접 타겟팅 (`#세션복구:{세션ID/번호}`)**:
   - 세션 식별자가 명시된 경우 즉시 해당 스냅샷을 적재하고 복구를 완결합니다.

## 4. 행(Hang) 원인 판별 및 세션 상태 표시 정책

### [규칙 4.1] 원인별 식별 기준
백엔드 및 프론트엔드는 다음 판별 기준에 따라 세션 상태를 사용자에게 실시간 표시합니다:

| 식별 코드 | 상태 명칭 | 기술적 판별 근거 | 권장 조치 |
|---|---|---|---|
| `HANG_OVERLOAD` | **일시 부하 지연** | HTTP 503 또는 에러 메시지 내 `model overloaded` | 1~3분 쿨다운 대기 후 재시도 |
| `HANG_QUOTA_EXHAUSTED` | **일일 쿼터 소진** | HTTP 429 및 `RESOURCE_EXHAUSTED` / `usage limit` | 한국시각 16:00 리셋 대기 또는 타 계정 전환 |
| `HANG_CONTEXT_BLOAT` | **세션 컨텍스트 포화** | 현재 세션 누적 토큰 150,000+ 및 브라우저 메모리 부하 | [긴급 소스 Push] 후 새 세션 복구 전개 |
| `HANG_INDETERMINATE` | **원인 불명 지연** | 10분(600초) 이상 응답 단절 및 네트워크 무반응 | 10분 경과 후 세션 강제 분할 및 백업 복구 |

### [규칙 4.2] 10분 대기 가드레일 (10-Minute Timeout Rule)
원인 불명의 행 발생 시 즉시 세션을 종료하지 않고 **10분간 대기 관측**합니다. 10분 경과 후에도 통신이 재개되지 않을 경우 `HANG_INDETERMINATE`로 확정하고 비-LLM 긴급 Push 및 새 세션 복구 프로세스를 가동합니다.
