# 개발 및 아키텍처 설계 가이드 (보완턴 규정 포함)

## 1. 아키텍처 기본 원칙
purePDFrend는 불필요한 보일러플레이트를 지양하고 작업 대상 코드만 집중 수정할 수 있도록 **실용적(Pragmatic) 아키텍처**를 지향합니다.

### 1.1 기본 구조: 심플 레이어 아키텍처 (Simple Layered)
- **적용 대상**: 초기 개발 단계, 단순 CRUD 및 UI 중심 기능
- **목적**: 파일 수와 추상화 계층을 최소화하여 인지 부하 감소 및 빠른 전달 속도 확보
- **계층 구성**:
  1. **Presentation / Route**: API 엔드포인트 및 React 컴포넌트
  2. **Service / Domain**: 비즈니스 로직 및 도메인 데이터 조작
  3. **Infrastructure / Persistence**: DB(PostgreSQL/SQL), 파일시스템, 외부 API

### 1.2 확장 구조: 헥사고날 아키텍처 (Hexagonal / Ports & Adapters)
- **전환 기준**: 도메인 복잡도가 증가하거나 외부 인터페이스(예: OCR 엔진 변경, 다양한 클라우드 스토리지 지원 등) 교체 요구가 발생할 때 유연하게 전환
- **도메인 격리**: 비즈니스 로직(도메인 엔티티 및 유스케이스)이 프레임워크 및 외부 라이브러리에 직접 의존하지 않도록 Port(인터페이스)를 정의하고 Adapter로 구현

---

## 2. OOP 기반 DDD (Domain-Driven Design) 설계 원칙
- **도메인 중심 캡슐화**: 상태와 비즈니스 행위를 함께 묶는 풍부한 도메인 모델 지향
- **필요한 코드만 수정**: 기능 추가 시 기존 도메인 경계를 침범하지 않고 명확한 책임(Single Responsibility) 단위로 수정

---

## 3. 개발 완료 후 보완턴(Refinement Turn) 프로세스
기능 구현이 완료되면 반드시 다음 6단계 보완 작업을 거쳐 코드 안정성을 확보합니다:

1. **구현 테스트코드 작성**: 주요 비즈니스 로직 및 API 엔드포인트에 대한 자동화 테스트 작성
2. **OOP 기반 DDD 설계 보완**: 불필요한 파일/코드를 정리하고 도메인 책임을 정돈
3. **심플 레이어 & 헥사고날 유연성 점검**: 서비스 복잡도에 따라 결합도를 낮추고 추후 아키텍처 전환이 가능하도록 구조 점검 - 적용가능한 디자인패턴 점검하여 반영
4. **보안 점검**: API 파라미터 유효성 검사, SQL 인젝션 취약점, 시크릿 하드코딩 여부 점검
5. **테스트코드 개선**: 테스트 실패 원인이 명확히 드러나도록 픽스처 및 어서션 보완
6. **코드리뷰 문서 작성**: `/docs/10.리뷰/YYMMDD_순번_작업내용.md`에 규정된 10대 헤더와 함께 리뷰 및 이슈사항 기록
