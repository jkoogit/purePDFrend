## 🎯 1. 교육 목표 및 배경 (Why Architecture Matters)

### 1.1 왜 소프트웨어 아키텍처를 변경해야 했을까요?
프로젝트 초기에는 모든 기능을 하나의 폴더(`src/components/`, `server.ts`)에 모아두어도 빠르게 개발할 수 있습니다. 하지만 시스템이 성장하고 **AI 에이전트 기능(거버넌스, 토큰 쿼터 감지, 작업 그래프 감사)**과 **순수 비즈니스 기능(PDF 뷰어, OCR 엔진, 가상 렌더링)**이 함께 섞이게 되면서 다음과 같은 심각한 문제가 발생합니다.

1. **원치 않는 결합(Tight Coupling)**: PDF 뷰어 컴포넌트를 수정하다가 AI 에이전트 감사 코드가 깨지거나, 반대로 에이전트 스토어가 변경되어 PDF 기능이 멈춤.
2. **테스트 불가능(Untestable)**: 네트워크나 원격 DB가 연결되어 있지 않으면 작은 단위 함수조차 테스트할 수 없음.
3. **AI 코딩 환경에서의 환각 및 침범**: AI 코딩 에이전트가 코드를 작성할 때 경계가 모호하면 순수 비즈니스 로직에 에이전트 제어 코드를 무분별하게 침투시킴.

이를 해결하기 위해 우리는 **OOP 도메인 주도 설계(DDD) 원칙**을 바탕으로, **도메인의 복잡도에 따라 아키텍처를 이원화(하이브리드)**하는 대규모 리팩토링을 단행했습니다.

## 🧭 2. 복잡도 기준 아키텍처 선택 의사결정 (Decision Matrix)

> 💡 **주니어 개발자가 가장 많이 하는 실수: "최신 유행 아키텍처를 모든 곳에 똑같이 적용하는 것"**  
> 모든 기능에 헥사고날(Ports & Adapters)을 적용하면, 단순한 설정 저장이나 화면 목록 조회에도 인터페이스, 어댑터, 포트 등 수많은 보일러플레이트 파일이 생겨 개발 생산성이 급격히 저하됩니다.

### 2.1 하이브리드 아키텍처 이원화 기준

```
                      [신규 기능 요구사항 인입]
                                 │
                                 ▼
                   ┌───────────────────────────┐
                   │ 외부 연동이 복잡하거나     │
                   │ 환경 변화(DB/LLM)가 잦은가? │
                   └─────────────┬─────────────┘
                                 │
                 YES ┌───────────┴───────────┐ NO
                     ▼                       ▼
       ┌────────────────────────┐  ┌────────────────────────┐
       │ 헥사고날 아키텍처       │  │ 레이어드 아키텍처       │
       │ (Hexagonal - Ports/Adap)│  │ (Layered - 3 Tier)     │
       ├────────────────────────┤  ├────────────────────────┤
       │ • 토큰 쿼터 감지 엔진   │  │ • 시스템 환경설정 관리 │
       │ • 멀티 OCR 파이프라인   │  │ • 문서 메타 목록 조회  │
       │ • 3계층 무결성 감사     │  │ • 단순 통계/이력 조회   │
       └────────────────────────┘  └────────────────────────┘
```

| 구분 | 헥사고날 아키텍처 (Hexagonal) | 레이어드 아키텍처 (Layered) |
|:---|:---|:---|
| **적용 영역** | **복잡 비즈니스** (외부 의존성 높고 변경 잦음) | **단순 비즈니스** (CRUD, 설정, 단순 조회) |
| **핵심 철학** | 의존성 역전 원칙(DIP), 도메인의 절대적 고립 | 단방향 흐름(Controller ➔ Service ➔ Repository) |
| **장점** | 외부 시스템(DB, LLM 공급자)이 바뀌어도 도메인 무수정 | 직관적이고 코드가 간결하며 개발 속도가 매우 빠름 |
| **단점** | 인터페이스 및 어댑터 작성 비용(보일러플레이트) | 상위 계층이 하위 계층 구현에 종속될 위험 존재 |

## 🛠️ 3. 아키텍처 전환 단계별 실무 가이드 (Step-by-Step)

### [Step 1] 도메인 경계 분리 및 폴더 구조 정립
기존 혼재되어 있던 `src/components/`를 3대 도메인으로 엄격히 분리합니다.

```
src/
├── ppdf/                     # [타겟 비즈니스 코어] 순수 PDF / OCR 도메인
│   ├── components/           # 가상 뷰어, 주석, OCR 렌더링 UI
│   ├── ports/                # 외부 시스템과의 계약(인터페이스)
│   └── index.ts              # ppdf 도메인 외부 공개 엔트리포인트
├── aiagent/                  # [에이전트 거버넌스] 하네스, 감사, 쿼터 도메인
│   ├── adapters/             # ppdf 포트 및 외부 시스템 구현체
│   ├── domain/               # 토큰 쿼터 감지, 무결성 감사 핵심 로직
│   ├── services/             # 설정, 문서 거버넌스 레이어드 서비스
│   ├── components/           # 작업 그래프, 대화 턴 추적, 문서 거버넌스 UI
│   └── index.ts              # aiagent 도메인 외부 공개 엔트리포인트
└── shared/                   # [공통 계층] 전사 공용 컴포넌트 및 유틸
    ├── components/           # Navbar, ErrorBoundary
    └── index.ts              # shared 도메인 공개 엔트리포인트
```

### [Step 2] 의존성 규칙 강제를 위한 TypeScript Path Aliases 설정
상대 경로 지옥(`../../../components/..`)을 방지하고 도메인 침범을 빌드 레벨에서 방지하기 위해 별칭을 구성합니다.

```json
// tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@ppdf/*": ["src/ppdf/*"],
      "@aiagent/*": ["src/aiagent/*"],
      "@shared/*": ["src/shared/*"]
    }
  }
}
```

```typescript
// vite.config.ts
export default defineConfig({
  resolve: {
    alias: {
      '@ppdf': path.resolve(__dirname, './src/ppdf'),
      '@aiagent': path.resolve(__dirname, './src/aiagent'),
      '@shared': path.resolve(__dirname, './src/shared'),
    },
  },
});
```

## 🧩 4. 실전 디자인 패턴 적용 사례 (Design Patterns in Action)

초급 개발자가 실무 코드에서 바로 이해하고 활용할 수 있는 대표 디자인 패턴 4가지를 프로젝트 실제 구현체와 함께 살펴봅니다.

### 4.1 전략 패턴 (Strategy Pattern) + 팩토리/레지스트리 패턴
- **적용 도메인**: `src/aiagent/domain/token-quota/`
- **문제 상황**: Gemini, Claude, OpenAI, DeepSeek 등 LLM 공급자마다 토큰 한도 초과 오류(429, Quota Exceeded)를 알리는 메시지와 JSON 응답 형식이 제각각임. 만약 `if-else` 문으로 작성하면 새로운 모델이 추가될 때마다 거대한 조건문을 수정해야 함(개방-폐쇄 원칙 OCP 위반).
- **해결책**:
  1. 공통 인터페이스 `ITokenQuotaStrategy`를 정의합니다.
  2. 공급자별 판별 알고리즘을 개별 전략 클래스(`GeminiQuotaDetectionStrategy`, `ClaudeQuotaDetectionStrategy`)로 구현합니다.
  3. `TokenQuotaStrategyRegistry`가 팩토리 역할을 하여 런타임에 에이전트 이름에 맞는 최적 전략을 찾아 실행합니다.

```typescript
// 1. 전략 인터페이스 (Contract)
export interface ITokenQuotaStrategy {
  readonly providerName: string;
  isQuotaExceeded(response: string, statusCode?: number): boolean;
}

// 2. 구체 전략 구현 (Concrete Strategy)
export class GeminiQuotaDetectionStrategy implements ITokenQuotaStrategy {
  readonly providerName = 'Google Gemini';
  isQuotaExceeded(response: string, statusCode?: number): boolean {
    if (statusCode === 429) return true;
    return response.toLowerCase().includes('resource_exhausted');
  }
}

// 3. 레지스트리/팩토리 (Registry / Factory)
export class TokenQuotaStrategyRegistry {
  private strategies = new Map<string, ITokenQuotaStrategy>();
  public register(key: string, strategy: ITokenQuotaStrategy): void {
    this.strategies.set(key.toLowerCase(), strategy);
  }
  public findStrategy(agentName: string): ITokenQuotaStrategy {
    return this.strategies.get(agentName.toLowerCase()) ?? new GenericQuotaDetectionStrategy();
  }
}
```

### 4.2 파사드 패턴 (Facade Pattern)
- **적용 도메인**: `src/aiagent/domain/audit/IntegrityAuditFacade.ts`
- **문제 상황**: 시스템 무결성 감사를 수행하려면 (1) 고아 레코드 검증, (2) 스토어-DB 패리티 검증, (3) 문서 SHA-256 해시 검증, (4) 정책 03-09 쿼터 위반 검증 등 여러 복잡한 서브시스템을 순차적으로 호출하고 점수를 합산해야 합니다. 클라이언트가 이 모든 복잡성을 알 필요는 없습니다.
- **해결책**:
  복잡한 4대 하위 시스템의 호출과 감점 계산 공식을 `IntegrityAuditFacade` 하나 뒤로 숨깁니다. 클라이언트는 단순화된 단일 인터페이스만 호출합니다.

```typescript
export class IntegrityAuditFacade {
  public static calculateIntegrityScore(indicators: ComprehensiveAuditResult['indicators']) {
    let deductions = 0;
    if (indicators.orphanRecords.orphanTasksCount > 0) deductions += 15;
    if (indicators.docsHashIntegrity.hashMismatches > 0) deductions += 15;
    if (indicators.policyQuotaGovernance.violationCount > 0) deductions += 20;
    // ...
    const score = Math.max(0, Math.min(100, Math.round(100 - deductions)));
    return { score, grade: score >= 95 ? 'A+ (PERFECT)' : 'WARNING' };
  }
}
```

### 4.3 어댑터 패턴 (Adapter Pattern) & 의존성 역전(DIP)
- **적용 도메인**: `src/ppdf/ports/IPdfServiceAuditPort.ts` ➔ `src/aiagent/adapters/PpdfAuditAdapter.ts`
- **문제 상황**: `ppdf`(타겟 PDF 비즈니스)는 독립적으로 배포되거나 오프라인 모드로 실행되어야 하므로 `aiagent`를 절대 직접 참조(import)해서는 안 됩니다.
- **해결책**:
  `ppdf` 내부에 원하는 규격을 포트 인터페이스(`IPdfServiceAuditPort`)로 선언하고, `aiagent`에서 이를 구현하는 `PpdfAuditAdapter`를 제공합니다.

```typescript
// [ppdf 내부] src/ppdf/ports/IPdfServiceAuditPort.ts - 순수 인터페이스
export interface IPdfServiceAuditPort {
  recordAuditLog(action: string, payload: Record<string, any>): Promise<void>;
  checkServiceIntegrity(): Promise<{ healthy: boolean; details?: string }>;
}

// [aiagent 내부] src/aiagent/adapters/PpdfAuditAdapter.ts - 어댑터 구현체
export class PpdfAuditAdapter implements IPdfServiceAuditPort {
  public async recordAuditLog(action: string, payload: Record<string, any>): Promise<void> {
    console.log(`[PpdfAuditAdapter] 중계 처리: ${action}`, payload);
  }
  public async checkServiceIntegrity() {
    const res = await fetch('/api/agent/audit/integrity');
    return await res.json();
  }
}
```

### 4.4 싱글톤 패턴 (Singleton Pattern) & DTO 패턴
- **적용 도메인**: `src/aiagent/services/SettingsService.ts`
- **특징**: 설정 정보는 애플리케이션 전역에서 단 하나의 인스턴스만 유지되어야 하므로 싱글톤 패턴을 적용하고, 계층 간 데이터 전달 시 불변 객체(DTO)를 반환하여 의도치 않은 상태 변이를 방어합니다.
